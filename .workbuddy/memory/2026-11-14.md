## 关键架构决策
1. **页面几何参数化**：PageGeometry 从 object 常量改成 data class（A4_PORTRAIT 595×842 / A4_LANDSCAPE 842×595）。
   PaperDocument / RenderedPdf 带 PageOrientation；PrintLauncher 用 `MediaSize.ISO_A4.asLandscape()`（javap 确认公开方法存在）。
   PDF 页面尺寸和打印框 MediaSize 必须同时改，否则驱动会二次缩放裁掉题号。
2. **练习纸走独立渲染分支**：PaperSection.grid 非空时 PaperRenderer 直接画「1 页铺满」，
   不套 FlowLayout（流式排版是按题量分页，画不满一页，和目标相反）。
3. **整卷连续流排版（本轮最重要的修复）**：
   旧版每个 section 各调一次 FlowLayout.layout() 再 pages.addAll，导致**每个大题强制另起一页**。
   实测一年级「计算题大全」被印成 7 页 / 99 题。
   改法：所有大题的块合并成一条流，标题 / 需书写过程的题用 FullWidthBlock 占整行；
   FlowLayout 重写成「段 + 贪心最矮栏」模型，支持整宽块落在页中、段内连续分栏、跨页续排。
   答案页单独成流（4 栏、startsOnFirstPage=false），保持另起一页。
4. **预览页加题的硬约束**：probeAppend() 在现有 paper 上追加题并试排，
   `addQuestions` 按 [n, .75n, .5n, .25n, 1] 依次试探，取第一个「不增页」的；
   `fillLastPage` 逐轮保留填充率最高且不增页的一版。加题后同步 counts 与卷头副标题。
5. **自动补题收敛**：旧版 suggestedExtra 不按栏数折算，5 轮把 46 题补到 99 题。
   现在 gain = TYPICAL_QUESTION_H / columns、横版用 410pt 页高、只在 `basePages == 1` 时补、
   MAX_AUTO_EXTRA = 24；预设题量调小（计算题大全 34 题 / 思维小练 25 题）。
   题量不足提示改成「缺口 > 20% 或末页 < 70%」才报，避免少两三题就误报。

## 实测发现并修掉的问题（重要，别再踩）
1. **卷头题数印错**：`PaperAssembler` 直接用 spec.subtitle，请求 37 题只生成 23 题时纸上印「共 37 题」。
   → 改为按 `paper.questions.size` 重算自动副标题，自定义副标题原样保留。
2. **单栏题型仍被塞进半栏**：PaperRenderer 整卷统一 `bodyColumns = maxOf(...)`，
   只判断 `answerLines > 0` 才包 FullWidthBlock；PaperComposer 里设 `columns=1` 根本没用。
   → 改成 `forceFullWidth = answerLines > 0 || section.columns <= 1`；
   英语 CLOZE/SENTENCE_ORDER 与 THEME_SORT/THEME_GROUP 的 `columns` 都改为 1。
3. **自动补题单栏场景整轮回退**：suggestedExtra 按全局 columns=2 估算，
   一次补 16 道单栏题顶到第二页 → 触发「不增页」break 回退，末页只剩 65%。
   → `suggestedExtra(ratio, fillType)` 按实际补的题型栏数折算；每轮只走估算量 80%，多轮逼近；
   `pickFillType` 跳过「请求数 > 实际生成数」的已抽干题型；扩充三年级自编句库与语法题库。
4. **同页连出两次同一个词**：两个 Theme 生成器加 `lastWord`，重抽最多 5 次避开上一题。
5. 低年级句库 / 题库扩容后「可用题量不足」误报消失。

# 2026-11-14 再续 · v0.7.3 TabBar 流畅度 + 去灰底

## 用户诉求

「左右滑动底部 TabBar 不顺滑卡顿」+「高亮之前还会有一个灰色背景要去掉」+「优化流畅度」。

## 灰底根因（已解决）

`DockItem` 用了裸 `Modifier.clickable { }`，默认吃 `LocalIndication`（M3 ripple）。
点下去先铺一层灰色涟漪，选中的淡紫胶囊跟不上，看起来就是「先闪灰再高亮」。
改 `clickable(interactionSource = remember { MutableInteractionSource() }, indication = null)`。
顺带把 `animateFloatAsState` 从默认 spring 换成 `tween(160, FastOutSlowInEasing)`，
默认 spring 末端有拖尾，点一下像要「顿一下」才到位。

## 卡顿诊断：结论是模拟器渲染上限，不是代码

方法：`adb shell dumpsys gfxinfo <pkg> framestats` 取逐帧分阶段时间戳（纳秒），
按 `IssueDrawCommandsStart - PerformTraversalsStart` 算 UI 线程，
`FrameCompleted - IssueDrawCommandsStart` 算 GPU/合成。**别只看 Janky% ，那个数没有定位价值。**

实测（metal 加速的 Apple M4 模拟器，1280x2400）：

| 场景 | UI 线程中位 | GPU 合成中位 | 整帧中位 |
|---|---|---|---|
| 旧版 v0.7.2 左右滑 | 4.8ms | 23.1ms | 30.8ms |
| 新版 v0.7.3 点 dock 切页 ×12 | 3.7ms | 20.5ms | 25.8ms |
| 错题本页（几乎空白）上下滚 | 2.8ms | 22.5ms | — |
| 打印纸页（36 张卡）上下滚 | 2.1ms | 21.0ms | — |

**决定性证据：空白页 22.5ms ≈ 36 张卡页 21.0ms，GPU 开销与内容多少完全无关。**
→ 这是模拟器每帧固定合成成本（Metal→GLES 转译 + host composition），真机通常 2-4ms。
→ 我先把四页改成 LazyColumn 重构成效在 UI 线程（本来就只有 4-5ms），所以 janky% 看不出变化，
   一度以为改动无效 —— 是误判，UI 线程才是能优化的部分，而它本来就不慢。

## 实际改的东西（都是真问题）

1. dock 去 ripple + 定长 160ms 选中动画（用户点名要的）
2. 点 dock 跳页的 `LaunchedEffect` 加 `!pager.isScrollInProgress` 守卫：
   松手时 settle 还没走完，又发 `animateScrollToPage` 去抢，两个动画互打断 = 顿挫
3. 四页签页 `Column + verticalScroll` → `LazyColumn` + `LazyListScope` 扩展

   `beyondViewportPageCount`，写错会编译失败）
4. `goTab` 里同步调 `refreshLists()`（两次 JSON 磁盘读 + 解析）挪走，
   新增 `suspend refreshListsAsync()` 走 `Dispatchers.IO`，由 pager 的 MORE 分支
   `LaunchedEffect` 触发。**不能在 LazyColumn 的 item 里放 LaunchedEffect**，
   列表项滚出屏会被回收后重跑

# v0.7.4 打印排版总修（versionCode 11）

本轮真正的主战场是「打印排版」。

## 排版引擎三处结构性改动

1. `TextPainter.wrap()` 加英文词边界
   - 逐字推进天生把 `worst` 断成 `w` + `orst`；语法表/音标表例词全是英文，断词比溢出更丑。
   - 断点两侧都是字母/数字时往前退到词边界（`len > 1` 保护，单词比整行还长才允许硬断）。
   - 教训：`NO_LINE_START` 避头逻辑必须放在退词之后，否则被吞进来的标点会把断点又推回词中间。

2. `TableBlock` 行高自适应 + `SplittableBlock` 按剩余高度切分
   - 旧版 `rowH = textSize * 2.2f` 写死且不折行 → 长例句横向溢出 + 纵向叠字。
   - 新版每格按列宽 `tp.wrap()`，行高 = `maxLines * 1.42 * textSize + padY*2`，
     `measure()` / `paint()` 共用 `cachedWidth + cachedRows` 同一份折行结果。
   - 新增 `SplittableBlock.split(tp, width, maxHeight)`，`FlowLayout` 放不下时先问能不能切一段；
     队列改成 `ArrayDeque`，切出来的后半截 `addFirst` 插回队首。
   - 同时删掉 `PaperTable.rowsPerBlock`（12 处调用点全删）：有了按高度切分，
     预切只会在同一页里画好几个重复表头。**这是关键取舍**：固定分块 vs 动态切分二选一。

3. 单页速查表拉高行距铺满
   - 九九乘法表原来只占页面上半截。`PaperRenderer` 里单表 + 单页 + 占用 < 74% 时，
     按 `cap*0.93/used` 算 `rowScale` 重排一次（上限 3.2），且必须仍是一页才采用。
   - **只放不能压**：`rowScale < 1` 会让 `row.height < lines.size * lineH`，
     垂直居中算出的 ty 变负 → 文字压到上一行，等于把这次修好的 bug 又放回去。

# v0.9.0 内置课标题库（cn-math-taxonomy）

用户需求原文：「https://github.com/xiaoyang111222/cn-math-taxonomy 这个内置进app，app不商用的」

## 许可判断（关键前提）

该仓库 **CC BY-NC 4.0**（署名 + 非商业）。用户明确说 App 不商用，所以可用，但必须：
- 「关于」页署名 + `assets/licenses/CN_MATH_TAXONOMY_LICENSE.txt` 全文；
- 许可证里写清「商业化前要删哪三个东西」（assets/taxonomy、CurricBankGenerators.kt、署名段落）。

这也是 README 那条「能整站内置的只有许可允许商用的」的唯一例外——文案已改成
「除课标题库外…」，不能再声称「不收录任何题库」（语文那批确实含课文配套题）。

## 数据管线（tools/import_taxonomy.py）

- 上游 3557 知识点 / 14375 题；裁到 1–9 年级五科 → **1939 知识点 / 7897 题**，14MB → 2.9MB。
- 字段压短键（i/ti/t/p/o/a/e/f/g），按科目拆五份 + `index.json` 只放统计（「内置内容」页读它显示题量，不碰 2.9MB）。
- **剔除依赖配图的题**：上游只有文字没图片，「如图，入射光线 AO 与镜面的夹角是 30°」印出来无解。
  只按「如图/下图/右图/左图/图所示/见图」判 → 删 25 道。
  ⚠️ 别把「数轴」「统计图」也算进来：那类题干通常已把数据写在文字里（"条形统计图上，喜欢苹果的直条对着 15"），
  误删会白丢几百道自洽题（第一版就误删了 62 道，用样例逐条核对才发现）。

## 代码结构

- `CurriculumBank`：懒加载 + 按科目分文件缓存 + `topicName()`（答案页/错题本要知识点名，不能显示 cnm_p123）。
- `CurricQuestion` 新增 `subject` 字段——跨科混池后必须知道每题属于哪科。
- `QuestionGenerator` 新增 `crossSubject` + `usableIn(subjects)`：
  原来 `availableFor` 里硬编码 `type == KNOWLEDGE` 特判，换成生成器自己判断是否该出现。
  课标题库靠 `CurriculumBank.countOf(subject, choice)` 决定——**语文没有填空题，勾语文时「知识点填空」自动隐藏**。
  `PaperComposer` 的大题科目前缀也改成按 `generator.crossSubject` 判断（跨科大题写「数学·」反而误导）。
- 两个生成器 `CurricBlankGenerator` / `CurricChoiceGenerator`（`CurricBankGenerators.kt`）：
  不用 BaseGenerator（它的去重按渲染后题干 hash，选项洗牌后同一题能重复进来），
  改成按**原题干** hash 进 `ctx.blocked`，洗牌后同步换算答案字母。

## 踩坑

1. **四年级卷子混进一年级题**：原 pool 是 `grade <= 当前`，一年级 difficulty 2 的题能直接漏进四年级。
   改三层收窄：本年级（≥16 道就用）→ 近两年 → 全部低年级；同层内再按难度筛。
2. **自检假通过**：`verifyChoice` 一开始拿 `pool(grade=9)` 找源题——修了年级收窄后九年级池不含四年级题，
   全部变成「找不到」。加 `findByPrompt()` 直查缓存，绕开 pool 的筛选。
3. **"看起来对"不等于对**：dumpQuestions 里加了机器核对（答案字母 → 题干里取出该选项文字 →
   回源题库比原文正确项），12 题 12 对。人眼扫一遍靠不住。

# v0.10.0 课本页 + 本地 PDF 打印

用户需求原文：「https://github.com/TapXWorld/ChinaTextbook/tree/master这个项目的课本可以内置到app」

## 结论：不能内置（三条硬指标）

| 检查项 | 实际 |
|---|---|
| 许可 | **GitHub API 返回 license: null，仓库没有 LICENSE 文件**，默认保留全部版权 |
| 体积 | 41.5 GB；人教版小学数学 12 册就 294 MB（单册 12–48 MB；>50MB 的被切成 .pdf.1/.pdf.2） |
| 格式 | 整本扫描件，不是练习纸 |

教材著作权属人教社等出版社，打进公开 APK = 二次分发。用 AskUserQuestion 给了三个方案，
用户**全选**：内置单元目录 + 教材链接清单 + 本地 PDF 导入打印。

## 关键设计决定（值得复用）

1. **单元目录不另做数据**：课标题库每个知识点自带 `c`（章节）字段，
   原文如「一年级上册 第1单元 5以内的认识和加、减法」/「七上 第二章 有理数的运算 2.2.2」。
   直接按 chapter 聚合就是教材单元，改题库单元自动跟着变，且题目/知识点/单元永远对得上。
2. **单元名要洗**：去前缀（`^X年级[上下]册`、`^[七八九][上下]`）+ **去末尾小节号**（`\s*\d+(\.\d+)+$`）。
   物理的 chapter 是**小节级**的，不洗的话八年级冒出八十个「单元」。洗后 80 → 22。
3. **按单元出卷靠 topicIds 传参**：PaperSpec / GenContext / pool 一路加 `topicIds`，
   非空时 pool 跳过「本年级→近两年」收窄（单元已框死年级，再扩会把别的单元混进来）。
4. **题量按单元实际题数封顶**（选择 ≤20、填空 ≤16），不拿别的单元充数。
5. **UI 必须诚实**：单元题不够时原逻辑会报「可用题量不足 0 题」（因为 fill<70 触发），文案自相矛盾。
   改成三种分支：单元卷→「这一单元的题已全部印上」；真缺题→报缺多少；否则才提示补满。
   并把「补满/加题」整块换成「改成按整册出卷」（否则是一个点了没反应的按钮）。
6. **本地 PDF 用流式适配器**：新写 `FilePrintAdapter`（64KB 缓冲），不用 `PdfPrintAdapter(bytes)`，
   三十多 MB 的教材整包读进内存会 OOM。
7. **PDF 只活在 cacheDir**，不当数据存、不上传 —— 用户自己的副本，App 只经手不持有。

## 踩坑

1. **年级解析抓错**：「英语（一年级起点）三年级上册」用第一个「X年级」匹配会全变成一年级，
   要取**最后一个**匹配。
2. **重名教材要去重**：同名既有整本又有分片的（8.5MB vs 88.7MB 两套扫描件），
   按 (学段,科目,出版社,年级,册次,标题) 去重，优先 k=1（用户不用自己合并）。
3. **Segmented 的尾随 lambda**：签名是 `style(items, selectedIndex, onSelect, modifier)`，
   尾随 lambda 会落到 `modifier` 上 → 必须写 `onSelect = {...}`。
4. **`when (screen)` 必须穷举**：加新 Screen 后 back() 里的 when 立刻编译报错，记得加分支。
5. **单元统计口径**：index.json 里先写的是原始 chapter 去重数（551），与实际 UI 合并后的
   407 对不上（物理 80→22）。改成按 (年级,学期,清洗后单元名) 去重才是界面上的真实数字。

## 实测数字

- 单元：407 个（数146/语132/英96/物22/化11）；教材链接：70 册（小48+初22）
- 按单元出卷：三年级数学第1单元 → 12 题 / 2 页；改成按整册 → 40 题 / 3 页 / 88%
- 本地 PDF：真实 PDF 1 页 / 竖版 / 缩略图正确 / 系统打印框预览正常
- APK：11.3 MB（教材目录 33 KB）
